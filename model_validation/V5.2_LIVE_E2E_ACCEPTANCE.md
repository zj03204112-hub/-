# V5.2 live prediction trace — acceptance status

This is an isolated integration path. It does not change V5.2 formulas, parameters, V5.1, or the default branch.

## Run
Manually dispatch the workflow on branch `feature/v52-live-prediction-e2e` with a China-time fixture date. Configure repository Actions variable `LEISU_EVENT_URL_TEMPLATE` only after verifying a public Leisu event endpoint and response schema. Template placeholders: `{event_id}`, `{date}`.

## Current gate
- The runner fetches Sporttery's public fixture list and fixed-bonus endpoint.
- It calls the existing `compare_models.model_lambdas(..., "v5.2", ...)` and `matrix(...)` without changing the calculation logic.
- It stores prediction snapshots and raw provider payloads in an append-only SQLite trace store, keeping provider event time separate from retrieval time.
- It requires an exact unique match in the model DB by normalized home/away and UTC kickoff date.
- It intentionally fails closed if the Leisu adapter is not configured or its response does not expose `eventId`, `homeTeam`, `awayTeam`. This prevents fabricated provider IDs.
- Post-match official result ingestion and cross-provider ID linking are not yet implemented in this first runner. Consequently this is not yet a full three-stage end-to-end acceptance and cannot justify promoting V5.2 to production.

## Release criteria
1. Configure and verify the Leisu endpoint/response contract.
2. Run a real upcoming match; prove unique internal ID + Sporttery matchId + Leisu eventId.
3. Add post-match result collection and require same-fixture ID linkage and official 90-minute score.
4. Confirm prediction timestamp < kickoff; preserve raw response hashes and separate source/retrieval timestamps.
5. Run integration and safety tests; publish a trace report. Only then propose a release PR; do not merge/promote while any gate is blocked.
