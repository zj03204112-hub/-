# V5.2 live prediction trace — acceptance status

This remains an isolated integration path. It does not change V5.2 formulas, parameters, V5.1, or the default branch.

## Implemented on the isolated feature branch
- `data_pipeline/run_v52_live_prediction.py`: calls the existing V5.2 lambda/probability functions and records pre-match predictions plus raw Sporttery/Leisu payloads in an append-only SQLite trace DB.
- `data_pipeline/finalize_v52_official_results.py`: separate result-ingestion utility that looks up official Sporttery results by the stored Sporttery `matchId`, checks home/away identity, and refuses to overwrite existing results.
- `.github/workflows/v52-live-prediction-e2e.yml`: compiles the runner and finalizer, runs append-only tests, and verifies the source database. Real prediction is only attempted on manual dispatch.

## Current verified status
- The observed GitHub Actions run `38853208221` passed compile, append-only tests, and source database integrity checks.
- That run **skipped** the real fixture prediction step because it was a push-triggered run, not a manual dispatch. It is not evidence of a real prediction or market capture.
- The finalizer was added after that run and has not yet been validated against a real completed fixture in CI.
- The Leisu adapter is still blocked: no verified public endpoint/response contract has been established. Do not set `LEISU_EVENT_URL_TEMPLATE` to a guessed URL. The runner intentionally stops rather than inventing a Leisu ID.
- Therefore no full E2E acceptance is claimed and the draft PR must not be merged/promoted to production.

## Required release gates
1. Establish a legitimate, accessible Leisu data endpoint or authorized feed and document its event ID, team names, kickoff and market timestamp fields.
2. Verify a real upcoming fixture against both Sporttery and Leisu; require unique mapping among internal `match_id`, Sporttery `matchId`, and Leisu `eventId`.
3. Capture raw market snapshots with source event time distinct from retrieval time; mark retrieval-time-only snapshots as such.
4. After kickoff, fetch the official full-time result and link it to the same stored Sporttery `matchId`; validate the score field against an actual response before accepting it.
5. Test prediction-time-before-kickoff, duplicate/ambiguous IDs, result conflicts, and append-only guarantees.
6. Publish trace evidence for at least one real fixture. Only then consider a release PR; do not modify V5.1 or historical predictions during this validation.
